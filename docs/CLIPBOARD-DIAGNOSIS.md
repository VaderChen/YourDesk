# Mac 剪貼簿調查狀態

流控修正隨 [1.26.0914 build 1049](RELEASE-1.26.0914-build-1049.md) 發行；下方保留修正過程與歷史測試條件。

更新日期：2026-09-15。

## 2026-09-15：macOS 網路卷宗存取修正，使用者實測有效

使用者回報：近端為 macOS 時，從 macOS 或 Windows 遠端複製檔案後，近端 Finder 的「貼上」反灰或沒有反應；近端為 Windows 則正常。經下列診斷與修正後，使用者已確認近端 Mac 的遠端檔案貼上恢復可用。此次回覆未逐一指定遠端系統及檔案種類，不擴大為所有組合均已重新驗證。

實機重現新增的證據：接收端完成清單驗證、WebDAV 掛載及 `writeObjects`，同程序讀回 1 個 file URL；但 macOS `pboard` 在同次操作明確回報 `Entry failed validation: […, public.file-url]` 與 `Some new entries were rejected! (1 > 0)`。因此原有「成功」只是本程序的寫入回傳與格式宣告，不能視為系統已接受。稍後另一程式覆寫文字，是後續事件，不足以解釋先前的檔案拒收。

同時，系統 TCC 預檢顯示 YourDesk 的網路卷宗存取尚待授權。新增存取檢查後，使用者以 build 1509 實測回覆「有用」，確認此修正對本次問題有效。macOS 接收端現在會先實際列舉貼上掛載，觸發正常的系統授權流程，成功後才發布 URL；封裝加入 `NSNetworkVolumesUsageDescription` 說明用途。若拒絕存取，回報授權操作說明並保留原剪貼簿；相同清單的重試不再建立新掛載，授權後需重新複製。

列舉只讀取目錄資訊，檔案內容仍在真正讀檔時才透過 P2P 傳輸。沒有關閉系統保護、重設權限或要求完整磁碟存取。Apple 的權限行為見 [NSNetworkVolumesUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsnetworkvolumesusagedescription)。

本機驗證結果：

- 原有手動觸發的 P2P Smoke，雙向各 2.8 MB 檔案經 WebDAV 讀取後內容一致。
- 另以兩個獨立程序、各自命名的測試剪貼簿，啟動正常 `Sync.Run` 自動偵測及同步，雙向各 3.29 MB 內容一致。測試未覆寫使用者的一般剪貼簿。
- 上述測試涵蓋清單發布及實際讀檔，不涵蓋 Finder「貼上」選單判斷，不能取代跨機操作驗證。

先前提供 macOS 診斷包 `1.26.0915 build 1248`。新增存取檢查的 `1.26.0915 build 1509` 已獲使用者實機確認；正式套件整理為 [1.26.0915 build 1524](RELEASE-1.26.0915-build-1524.md)。這項接收端修正只需更新近端 Mac。

變更已通過語法／編譯檢查與雙程序自動同步 Smoke；紀錄確認存取檢查、發布完成後才出現 GET。另以隔離測試模擬目錄存取遭拒，確認原剪貼簿保留，重試相同清單僅建立一次掛載。自動測試未操作使用者的系統授權；Finder 實機可用的結論另依據使用者更新後的確認。

此次新增的診斷沿用「封包分析」開關及有界背景日誌，事件名稱為 `clipboard`；以 `offer` 關聯同一份清單。只記錄階段、數量、格式宣告及結果，不記錄剪貼簿內容、檔名或路徑。

| `stage` | 能確認的進度 |
| --- | --- |
| `source-files-observed`、`offer-send` | 本端偵測到檔案並送出清單 |
| `offer-received`、`offer-complete` | 遠端清單抵達且完成格式驗證 |
| `offer-rejected` | 能力、容量或本機剪貼簿已變更等拒絕原因 |
| `publish-start`、`mac-mount-start`／`mac-mount-finished` | 開始發布及 WebDAV 掛載結果 |
| `mac-mount-access-start`／`mac-mount-access-finished` | App 是否能實際列舉掛載，以及是否遭拒絕存取 |
| `mac-pasteboard-write`、`mac-pasteboard-formats` | 本程序寫入 API 的回傳與 file URL 格式宣告，不保證系統已接受 |
| `publish-finished` | 本端發布流程完成或失敗；不等同 Finder 已貼上 |
| `mac-dav-request` | 系統首次查詢中繼資料或開始 GET 讀取，每份清單每種方法最多一筆 |
| `mac-mount-closed` | 掛載資源已進入清理，後續不再供應該清單 |

格式檢查只讀取宣告，不讀取延遲內容。封包分析關閉時不執行額外的原生格式檢查。未更換剪貼簿格式、未預先下載完整遠端檔案，也未改變既有流控。

## 慢速接收與網路回呼阻塞

新版剪貼簿通道原本已使用非阻塞的 128 槽接收佇列，沒有像影像 `Submit` 一樣直接等待空槽；但後續磁碟／系統剪貼簿工作者處理太慢，仍可能塞滿佇列而關閉剪貼簿通道。舊版文字備援另外會在有序控制回呼內持鎖寫入系統剪貼簿，確實有阻塞 DataChannel 接收的同類風險。

本次保留可靠檔案內容，接受降低傳輸速度：

- 兩端公告 `clipboardWindow` 能力後，以應用層實際處理完成量歸還傳送額度；額度不足時等待的只有送出工作者。普通資料與 pull 讀取請求／回覆、完成 ack 各有 32 筆額度，合計最多 64 筆、每筆最多 20 KiB，低於 128 槽接收上限。
- 普通資料由接收工作者處理後才歸還額度。pull 資料及 ack 由路由工作者交接後歸還；兩類各自等待，不讓普通資料滿載擋住原生剪貼簿正在等待的讀取回覆。各類送出仍共用同一個緩衝檢查鎖，保留 64 KiB／20 KiB 的既有送出上限。
- 累計額度確認由 control 通道傳送，約 10 ms 合併一次；重複、倒退或超過送出量的確認不增加額度。它只代表接收工作者已消費資料，不代表整份傳輸成功；既有大小、摘要和完成 ack 驗證仍保留。
- 控制事件改由單一、有界工作者依序執行。舊版文字寫入完成後才執行後續貼上按鍵；ping、指令回覆與額度確認先由接收回呼處理，不等待原生寫入。接收壅塞時可略過新滑鼠移動，保留剪貼簿、按鍵與按鈕順序；不可遺失事件仍超過上限時明確結束連線，不默默丟棄。
- 等待可取消，沿用傳輸逾時與斷線錯誤，沒有增加固定批次 sleep、無限重試或背景重連。舊端沒有額度能力時沿用原有緩衝門檻，不會等待它無法提供的確認；要讓兩個傳輸方向都具備接收流控，兩端均須更新。舊端或異常傳送超出接收佇列時的防護仍保留。

驗證使用獨立本機 WebRTC 連線，暫停接收至額度用盡，確認傳送等待、心跳可往返、優先讀取回覆可穿過；恢復後雙向各 3.125 MiB 的每筆資料與順序均比對一致。另驗證取消、累計確認及模擬原生文字寫入阻塞時的按鍵順序。這次測試不讀寫系統剪貼簿，也不操作正在使用的遠端連線；跨機 Finder 實際貼上仍應實測。

## 2026-09-10 歷史實機結果

### 當時的實機確認

使用者於發布前再次測試並更正結果：**Mac 對 Mac 的文字、圖片及雙向檔案複製均已確認可用**。此最新結果取代先前「單向可用」及「雙向失敗」的暫時判斷；Release 不再列出檔案複製失效警告。

### 當時已完成的修正與證據

系統剪貼簿讀取可能等待資料提供者。原本讀取時持有的狀態鎖也用於接收端發布，因此存在讀取等待阻塞接收的風險。現有修正將內容讀取移出狀態鎖，保留發布前的剪貼簿序號檢查，避免覆蓋使用者新複製內容。

macOS 讀取端略過系統標記的跨裝置剪貼簿內容；寫入使用 NSPasteboardContentsCurrentHostOnly，降低跨裝置回傳循環風險。最新實機確認已可使用，但尚未透過控制變因實驗確認是哪一項改動消除原始問題。

本機 P2P smoke 曾完成雙向文字與檔案內容比對；實機調查亦曾收到檔案清單、建立 WebDAV 掛載並核對完整內容。但發布 API 成功回傳與檔案傳輸成功，不代表 Finder 能正常貼上。

### 當時的驗證限制

本機測試兩端共用剪貼簿，採手動觸發傳輸，未涵蓋兩台 Mac 的完整複製偵測與 Finder 操作。先前僅有獨立程序手動重新發布成功，當時不足以宣稱修復；本次可用結論另有使用者最新實機確認，不是從該 smoke test 推論。

曾試驗直接剪貼簿項目、舊式檔案清單格式、程序外發布、發布後核對及短暫重試，皆未證明解決自動流程，候選變更已撤回。沒有足夠證據將原因歸給 AnyDesk，亦未確認單一系統元件為根因。
