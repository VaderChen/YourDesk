# 畫面增強：超解析度與補幀研究

## 本次發行狀態

以下研究與階段紀錄保留歷史設計；目前採用寬高 75%、三種策略、FSR 1 與 QuickSRNet Small／SESR M5 Core ML 模型，已移除 PiperSR。未實作補幀。最新行為以 README、QUICKSRNET.md 與 STREAM-CONFIG-DESIGN.md 為準。

研究日期：2026-09-09。本文保留導入設計；第一階段介面與 FSR 1 已接入，詳見文末實作現況。尚未取得實機效能或畫質驗證結果。

## 目前行為修正

依實機回饋，影像增強改為只降低傳輸解析度，不再強制碼率折半。標準／高畫質恢復原有品質控制；低流量維持原本的碼率預算，不再額外除以二。真實 FPS 不變。以下研究與第一階段紀錄中的碼率折半方案已被此修正取代。

## 原始需求與建議

新增設定分頁「影像增強」，位於「串流方式」與「關於」之間。開啟後，來源以 GPU 將寬、高各縮為 50%，設定原基準碼率的 50%；接收端放大，並可選每兩張真實影格補 1 或 2 張，對應約 2× 或 3× 顯示 FPS。

「縮減一半」在此沿用既有低流量的寬、高各半定義，例如 3840×2160 → 1920×1080，像素總量為四分之一。若真實輸入為 30 FPS，補幀目標為 60／90 FPS，仍受螢幕更新率及 GPU 預算限制。

建議先導入 **FSR 1 空間放大＋獨立碼率控制**，再研究影片用光流補幀。XeSS 與時域 FSR 不適合直接接到目前僅有桌面影像的管線。補幀在 遠端顯示 進行，不增加網路傳送影格；來源端 GPU 縮圖失敗才使用 CPU 縮圖。

## 技術選擇

| 技術 | 與目前桌面串流的適配程度 | 建議 |
| --- | --- | --- |
| FSR 1 | 空間放大，以影像為輸入，包含 EASU 放大及 RCAS 銳化 | 第一階段候選；評估移植至現有 GPU shader 管線 |
| XeSS-SR／時域 FSR | 需要桌面擷取沒有提供的時域渲染資訊 | 暫不作正式選項 |
| XeSS-FG | 需要深度、動作向量及特定呈現整合 | 暫不導入 |
| FSR Frame Interpolation | 除光流外仍需要深度及動作向量相關資源 | 不能直接當作兩張影片影格的通用補幀器 |
| 影片光流補幀 | 從連續影像估計運動，較符合串流輸入 | 第二階段先研究 2×，再評估 3× |

FSR 1 的 EASU／RCAS 適合先驗證 GPU 放大，但不能保證還原縮圖時丟失的小字與細線。[AMD FSR 1](https://gpuopen.com/fidelityfx-superresolution/)

XeSS-SR 的整合需要動作向量、抖動等渲染資訊；時域 FSR 同樣依賴渲染器輸出。目前收到的壓縮桌面不包含這些資料，影像光流也不能直接視為等價的引擎動作向量。[Intel XeSS-SR](https://www.intel.com/content/www/us/en/developer/articles/technical/xess-sr-developer-guide.html)、[AMD 時域超解析度](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-temporal/)

XeSS-FG 現行指南列出 Windows x64、D3D12 與 XeLL 整合要求，必須提供動作向量及深度；已支援符合條件的非 Intel GPU，但其最多補 1 張。多張補幀須查詢裝置能力，不能承諾所有顯示卡都支援 3×。指南建議最低真實輸入 40 FPS、60 FPS 較佳；目前 YourDesk 預設輸入偏低。[Intel XeSS-FG 指南](https://github.com/intel/xess/blob/main/doc/xess_fg_developer_guide_english.md)

FSR Frame Interpolation 即使與超解析度分離，仍有深度、動作向量等準備資源，不能只提供前後兩張桌面圖就完成正式整合。[AMD Frame Interpolation](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/frame-interpolation/)

## 平台策略

| 遠端顯示 平台 | 放大第一階段 | 補幀研究方向 |
| --- | --- | --- |
| Windows x64，Intel／AMD／NVIDIA | 共用空間放大 shader，依實際 GPU 能力啟用 | 共用影片光流介面；廠商加速作可選後端 |
| macOS | 共用 shader；另評估 MetalFX Spatial | Metal 光流估計與影格合成，需量測延遲及耗電 |
| Windows ARM64（WOA） | 優先共用 shader，確認原生 ARM64 與 GPU 支援 | 未驗證前停用，不載入 x64 SDK DLL |

macOS 可用 MetalFX Spatial 作候選後端，但須執行裝置支援查詢；不以作業系統名稱直接判定可用。[Apple MetalFX Spatial](https://developer.apple.com/documentation/metalfx/mtlfxspatialscaler)

NVIDIA FRUC 是針對影片補幀的候選，依賴受支援的 NVIDIA 光流硬體，不能覆蓋 Intel／AMD／Mac。它適合獨立後端驗證，不能成為全平台唯一實作。[NVIDIA FRUC](https://docs.nvidia.com/video-technologies/optical-flow-sdk/nvfruc-programming-guide/index.html)

Intel VPL 的影格率轉換能力須查詢，不能將重複影格當作光流補幀。Apple Vision 能估計光流，但不是完整即時補幀器，仍需自行處理遮擋與合成。[Intel VPL](https://intel.github.io/libvpl/latest/programming_guide/VPL_prg_vpp.html)、[Apple Optical Flow](https://developer.apple.com/documentation/vision/vngenerateopticalflowrequest)

## 現有程式需要調整之處

以下依目前工作目錄程式碼檢查，屬靜態分析：

- `cmd/client/main.go`：預設 12 FPS；低流量會提高至約 18 FPS，並已有寬、高各半的縮圖邏輯。新功能必須統一計算有效解析度，避免與低流量疊加成四分之一寬、高。
- 同檔標準／高畫質使用品質控制（rate = 0），低流量才設定目標碼率。因此「碼率一半」須先定義原始解析度、編碼格式及真實 FPS 對應的基準 B，再設定 B/2；不能把品質參數除以二當作碼率減半。
- `internal/desktop/scale_gpu_*.go` 已有 GPU 縮圖入口，可延伸共用政策與 CPU fallback。
- `cmd/remote/resize.go` 現有 shader 只接受縮小尺寸，需新增放大處理，不能直接視為已有超解析度。
- `cmd/remote/main.go` 仍透過 `WritePixels` 上傳影格；Windows 解碼及縮圖路徑也有 CPU RGBA／GPU 回讀。硬體解碼不等於完整管線零拷貝，新增效果前須評估這些傳輸成本。
- `internal/p2p/peer.go` 的 `Frame` 有序號，未有擷取時間戳、深度或動作向量。補幀需版本化時間戳與能力協商，不可直接改既有標頭破壞舊版連線。

目標碼率減半不代表總 RX 精確減半：音訊（若未來加入）、剪貼簿、協定開銷、編碼器波動與場景內容都會影響總量。應分別呈現影片目標碼率及實際影片流量。JPEG 沒有相同的影片 CBR 行為，需另作速率控制或明示無法精確限制。

## 延遲與顯示行為

補幀提高的是顯示 FPS，不會提高遠端輸入採樣率或真實內容更新率。若採等待下一張真實影格的插值設計，約一個來源影格週期的緩衝就可能是：

| 真實 FPS | 一個來源影格週期 | 2×／3× 顯示目標 |
| --- | --- | --- |
| 12 | 83 ms | 24／36 FPS |
| 18 | 56 ms | 36／54 FPS |
| 30 | 33 ms | 60／90 FPS |
| 60 | 17 ms | 120／180 FPS |

這是緩衝設計的量級估算，並非實測延遲；另外還有運算與呈現等待。第一個影片補幀原型以穩定 30 FPS 以上為研究目標，並非 XeSS 的官方最低要求。預設補幀關閉，低 FPS、網路不穩或 GPU 超時時回到真實影格。

切換螢幕、解析度、全螢幕、場景跳變及時間戳不連續時清空歷史，禁止沿用錯誤的前一張畫面。設定切換與資源重建不得阻塞 UI。

遠端顯示 工具列應在影像增強後繪製。游標若仍燒入桌面影像就可能產生殘影，需另評估游標分離。遠端桌面的文字與 UI 已合成在影像內，無法像遊戲 HUD 一樣直接排除補幀。

## 新增「影像增強」設定頁

此表為完整介面規格；目前僅實作主開關與固定參數，詳見文末。尚未完成的後端不提供可啟用的選項。

| 設定 | 初始值／行為 |
| --- | --- |
| 啟用影像增強 | 關閉；開啟後協商雙方能力 |
| 超解析度 | 自動；第一階段僅列實際完成的後端，例如 FSR 1 |
| 傳輸尺寸 | 寬、高各 50%，旁邊顯示實際來源與傳輸解析度 |
| 目標碼率 | 基準 50%，同時顯示實際 Mbps 目標 |
| 銳化程度 | 提供保守預設，避免文字過度銳化 |
| 補幀 | 關閉／2×（補 1 張）／3×（補 2 張）；未支援項目停用並說明原因 |
| 顯示 FPS 上限 | 不超過螢幕更新率與裝置可用能力 |
| 執行狀態 | 實際演算法、真實 FPS、顯示 FPS、目標碼率及 fallback 原因 |

開關與設定持久化，多國語同步；偏好儲存在 遠端顯示，能力依每次連線重新判斷。舊版來源不支援新協定時維持既有串流，顯示限制，不偷偷套用其他畫質設定。關閉功能後還原原畫質政策，避免將減半後的值寫回基準造成累積折半。

## 實作順序與驗收規劃

1. 統一畫質政策、能力協商與明確碼率基準；新增設定頁及持久化。先完成 GPU 縮圖、遠端顯示 空間放大、失敗回退，再開放主開關。
2. 整理影格時間戳、GPU 資源重用及呈現排程，區分真實／生成／顯示 FPS。先確認降傳輸成本能否提高真實 FPS。
3. 製作影片光流 2× 原型，比較文字、捲動、視窗拖曳、影片與游標殘影。性能及延遲可接受後才開放實驗性選項。
4. 再評估 3× 與個別廠商後端；無能力的設備保留放大，補幀停用。CPU fallback 不強行執行高成本補幀。

正式驗收應以相同來源內容比較影片流量、真實與顯示 FPS、GPU 時間及操作延遲，另檢查解析度切換、裝置失效與舊版相容性。此處只列後續驗收建議，本次未進行額外測試，也未宣稱已達成減半流量或倍增 FPS。


## 第一階段實作現況（2026-09-09）

已新增「影像增強」分頁及預設關閉的持久化開關，包含英文、日文、韓文翻譯。遠端顯示 定期讀取共用偏好，無須重啟連線即可套用。這次依使用者指示保留既有真實 FPS，未加入補幀。

FSR 1 EASU／RCAS 已移植為 Kage GPU shader，使用完整 12 點 EASU 與獨立 RCAS pass；使用精確浮點運算及邊界保護，因此不是 AMD 二進位 SDK 或逐位元一致實作。授權保留在原始碼與 App 的關於頁。縮放資源只在尺寸穩定後重建，沒有新影格時重用結果；shader 編譯失敗時維持既有串流。

新版來源在能力公告中回報支援，遠端顯示 才會提出增強請求。原始寬、高各半只套用一次，來源沿用 GPU 縮圖／CPU fallback。舊版來源維持既有模式。H.264／HEVC 的標準與高畫質基準預算暫定為原始像素數 × 基準 FPS × 0.25 bit，上下限為 0.512～32 Mbps，再取 50%；低流量則將其原有目標碼率減半。這是可重現的預算，並非對先前品質模式實測流量保證減半。JPEG 只縮圖。

此階段只有固定放大與保守銳化參數；補幀明示尚未啟用。仍需實機觀察文字品質及 GPU 成本，尚未宣稱具有更高顯示 FPS。編譯檢查不等同於跨平台實機驗證。


## Core ML 與狀態圖示接入（2026-09-09）

超解析度已改為「可使用／不支援」下拉選單。程式啟動時背景載入並檢查 Core ML 模型，成功後才列為可使用；偏好持久化，已開啟的 遠端顯示 也會重新讀取。Windows／非 Apple Silicon 平台列為不支援，不影響 FSR 1。

目前內附 PiperSR 2× 的固定 128×128 RGB 輸入模型，输出 256×256。此版本並非模型介紹所稱的任意尺寸介面：實際編譯 metadata 顯示固定尺寸，因此使用 16 像素邊界的重疊分塊。模型位於 `internal/superres/PiperSR_2x.mlpackage`；來源為作者 Hugging Face 的 `ModelPiper/PiperSR-2x`，固定修訂 `8daecfccbbe023de6580e7eecbff3d44a51d0b13`。模型權重未修改，署名及 CC BY 4.0 授權內附在 App 關於頁。未使用該模型專案的 AGPL 推論程式碼。

Core ML 使用系統自動配置運算裝置，不宣稱每個運算都在 ANE 或 GPU。原生推論在單一背景工作執行，最多保留一張待處理影格；顯示器、尺寸或設定變更會使舊結果失效。推論錯誤或分塊處理超過時間預算時回退 FSR 1 並記錄原因。時間預算在分塊間檢查，不能中斷正在執行的單次 Core ML prediction。

目前是實驗性串接，固定小尺寸模型的分塊可能明顯限制速度，尚未量測整張桌面的延遲或畫質。來源真實 FPS 維持不變，但接收端推論速度不保證跟上。QuickSRNet、SESR、ESPCN 與 Real-ESRGAN Anime 保留為後續比較候選。

遠端顯示 在編碼圖示左側新增影像增強圖示。灰色表示未生效或等待確認；亮綠色需要來源回報已開啟且本機實際採用增強輸出。Hover 顯示演算法、來源／傳輸／顯示尺寸、目標碼率、補幀狀態與回退原因。舊版來源尚未回報完整狀態時會顯示等待訊息，不假設它已生效。
