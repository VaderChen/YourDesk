# 串流停滯與連線存活

本輪修正隨 [1.26.0914 build 1049](RELEASE-1.26.0914-build-1049.md) 發行；下方保留修正過程與歷史測試條件。

## 2026-09-17：Windows 長時間串流停滯檢查（尚未發行）

新增使用者回報：Windows 長時間連線後也會停止更新串流，但比 macOS 更晚發生。下方「僅 macOS」描述是當時觀察，不代表 Windows 不受影響。目前尚未取得停滯當下的 Windows 堆疊或實機重現，因此不能確認此回報的根因。

後續確認：Windows 是被控端，約半小時後畫面與鍵鼠同時失效，但仍顯示連線。GPU 防護不能單獨解釋此症狀；新增下列共用存活偵測：

- 心跳持續失敗且 30 秒沒有接收進展，結束失效連線；即使還有零星接收流量，心跳連續失敗達 90 秒亦結束。期限從首次心跳失敗開始計算，另有 5 秒檢查間隔及單次最多 5 秒等待。
- 心跳送出使用每個監視器唯一的工作者；底層 Send 忽略 context 時，監視器仍能逾時，不會反覆增加被卡住的工作者。此機制不能強制終止底層呼叫，卡住的工作者須等待底層返回。
- 控制事件正在處理超過 30 秒，即使獨立 ping 正常，也標記工作階段失效並非同步關閉連線。沒有控制事件的閒置工作者不計時。這是停滯偵測，不保證能強制解除 Windows API 或相關資源清理的阻塞。
- 開啟「封包分析」後，每 10 秒記錄 `application-traffic`：送出／接收位元組、接收應用訊息數與觀測秒數。零則為 `no-receive`，平均每秒不超過 0.2 則為 `low-receive`，其餘為 `active`。這是診斷門檻，單純低流量不斷線；DataChannel 訊息不是 UDP 封包，實際 socket 封包量仍看既有 `udp-socket`。
- `heartbeat-failed` 記錄心跳已達失效門檻；`control-worker-stalled` 記錄控制工作者停滯。堆疊沿用封包分析開關與每程序最多兩次的限制。

虛擬時間回歸測試涵蓋：無接收但心跳正常持續一小時、心跳失敗但仍持續收資料、底層心跳呼叫不返回、單個控制事件卡住但佇列未滿、工作者閒置／恢復／取消，以及無流量與低流量分類。這些測試驗證失效偵測，不代表已修復實機半小時後最初發生阻塞的原因。

`754660b` 的非阻塞解碼交接已由 Windows 共用，無須重複移植。另查到 Windows 三處 GPU 讀回使用 `Map(D3D11_MAP_READ, 0)`：DXGI 桌面擷取、D3D11 縮圖／編解碼讀回，以及硬體解碼能力探測。GPU 未完成 Copy 時，這些呼叫會等待；外層 Go worker 亦會持續等待，無法進入既有失敗備援。

上述讀回改用 `D3D11_MAP_FLAG_DO_NOT_WAIT`，只對 `DXGI_ERROR_WAS_STILL_DRAWING` 重試；首次忙碌時 Flush 送出排隊命令，每次等待 1 ms，累計 2 秒仍忙碌便返回 `WAIT_TIMEOUT`。裝置移除與其他錯誤立即返回。成功 Map 後仍由原呼叫端 Unmap；失敗不讀取像素。DXGI 錯誤沿用 GDI 備援與 30 秒重試；縮圖及編解碼錯誤沿用原有備援，並新增 Windows 硬體解碼失敗原因日誌。

這是 GPU 讀回等待的防護，不是原生驅動呼叫的強制中止機制：若驅動卡在 Map 呼叫本身、Flush、Media Foundation、GDI 或資源釋放內，仍不保證能在 2 秒返回。未新增超時後遺留原生 worker 的 goroutine，也未加入自動重連。

原生替身測試使用正式 `readback.h`，覆蓋立即成功、暫時忙碌、持續忙碌逾時、裝置移除、其他錯誤，以及 100,000 張影格中途發生一次逾時後繼續處理。執行方式：

```sh
c++ -std=c++17 -Wall -Wextra -Werror internal/winmedia/testdata/readback_test.cpp -o /tmp/yourdesk-readback-test
/tmp/yourdesk-readback-test
```

仍須在 Windows 實機執行超過原本重現時間的動態畫面測試，並分別記錄 Windows 是被控端或觀看端。靜止桌面零 FPS 屬正常；以持續變動的時鐘／影片確認更新，停滯時另確認控制通道、鍵鼠與硬體解碼失敗日誌。單元測試不代表這次長時間停滯已在實機修復。

## 遠端桌面閒置自動關閉（尚未發行）

設定頁「斷線後自動關閉視窗」下方新增「長時間未操作自動關閉」，預設關閉。啟用後，每個遠端桌面視窗各自計時；連續 15 分鐘沒有操作，結束該連線並關閉該視窗，不受「斷線後自動關閉視窗」開關影響。只關閉遠端桌面工作階段，不結束主程式或被控端 Host；此設定不適用獨立命令列視窗。

滑鼠相對上次有效位置移動超過 4 個遠端畫面像素、鍵盤按下（包含原始按鍵）、滑鼠點擊與滾輪操作會重設計時。4 像素半徑內抖動不更新錨點，慢速位移會累積到超過門檻；重送同座標的 move、心跳、畫面更新及自動釋放按鍵不算操作。閒置視窗失去焦點仍會計時；啟用設定或新連線時從零起算，關閉設定即停止計時。偏好儲存在 `closeWhenIdle`，既有設定檔缺少此欄位時保持關閉。

## 2026-09-14：已處理解碼佇列阻塞造成的串流穩定問題

修正提交：[`754660b`](https://github.com/VaderChen/YourDesk/commit/754660b3dec39bed957997ab9fe9f7c6727ce236)。目前回報的停滯／斷線只發生在 macOS 對 macOS；其他平台尚未觀察到相同問題。以下修正在 build 2323 發布之後加入主分支，既有 build 2323 套件不包含此修正。

先前 顯示區域 在 WebRTC 畫面接收回呼使用 `Consumer.Submit`。兩個交接槽位包含正在解碼的影格；解碼變慢或停住時，滿載的 `Submit` 會等待空槽，連帶阻塞 DataChannel 接收回呼。現在新增非阻塞的 `TrySubmit`，一般 顯示區域 與背景診斷均改用此入口；滿載時立即返回並略過目前新影格，讓網路接收繼續執行。原有已排隊影格保持順序，沒有擴大佇列。

一般 顯示區域 沿用影格序號缺口檢查、解碼器重設及關鍵影格恢復流程。壅塞時可能短暫掉幀；此修正處理解碼速度對網路接收的阻塞，不是強制終止卡住的原生解碼器，也不依賴背景自動重連或斷線續傳。

回歸測試包含佇列滿載即返回，以及 worker 停住期間連續 100,000 次交接嘗試均不阻塞。原有順序與取消測試仍保留。同步前已通過 `go test -race ./internal/streampipeline ./internal/p2p`，以及啟用 FFmpeg／TurboJPEG 的 macOS 顯示區域 編譯與影格合成 Smoke。這項可重現的佇列阻塞已修正；下方 build 2323 段落保留當時觀察，不代表新版仍未處理此缺陷，也不把所有網路中斷都歸因於此問題。

## build 2323 驗證狀態

目前回報的停滯／斷線問題只發生在 macOS 對 macOS；其他平台尚未觀察到相同問題。升級整組 Pion 傳輸套件後，使用者回報單一連線及同時連線兩個遠端均維持穩定，較先前測試版本改善。這是目前測試環境的觀察，**尚未完全確認原先 Mac 對 Mac 停滯／斷線問題已解決**，也未確認具體根因；長時間與大檔案傳輸仍需驗證。本版未加入背景自動重連或斷線續傳，穩定性觀察不是由自動重連掩蓋中斷所得。

P2P 控制通道開啟後，每五秒嘗試一次已公告的 ping 指令。單次最多等待五秒，成功會重設失敗狀態。心跳逾時但仍收到 DataChannel 資料時保留連線；只有心跳持續失敗且至少 30 秒沒有接收進展，才記錄原因並關閉失效連線，使既有斷線流程可執行。單純本機送出增加不算接收進展。這不等同自動重新連線，也不能修復已阻塞的原生編碼器。

只有對端已公告 ping 能力才啟用；舊端未公告時不因不支援而誤斷線。MCP 主動暫停串流仍保留控制通道，照常確認存活；靜止桌面 FPS 為零本身不是斷線依據。

本輪測試涵蓋暫時失敗後重設計數、連續失敗關閉，以及不支援能力時跳過檢查。這是失效偵測補強，不能僅據此宣稱 Mac 對 Mac 停滯的根因已修復。

連續失敗期間，開啟封包分析才取樣底層流量、DTLS 狀態，以及 SCTP 接收視窗、擁塞視窗、往返時間和各 DataChannel 待送量。診斷取樣改為有期限的背景工作，移除重複的同步停滯取樣。紀錄不包含 IP、SDP、密碼或傳輸內容；接收視窗仍有餘裕不代表資料通道必定正常。

## macOS 診斷版

診斷紀錄由「設定 → 關於 → 封包分析」開關控制，預設關閉；開啟才排入 LOG，關閉後略過尚未處理的舊事件，已在途的檔案 I/O 仍可能完成。舊建置旗標不再自動啟用紀錄。診斷版沿用 Developer ID 簽章與 Apple 公證流程。

Host、顯示區域 與主介面各自把 JSONL 寫入 `~/Library/Caches/YourDesk/Logs/`，檔名包含啟動時間、角色及 PID。每十秒記錄傳輸與 SCTP 位元組計數、視窗、RTT、通道狀態及待送量；ping 逾時時擷取 Go goroutine 堆疊，每程序最多兩次、每次最多 512 KiB。每個紀錄檔最多 5 MiB，開啟新紀錄檔時清除七天前的 JSONL。紀錄不擷取畫面、鍵盤、剪貼簿、密碼或命令內容；堆疊仍可能含函式名稱與數值參數，請作為私人診斷資料處理。

日誌改用有界背景佇列，每秒批次同步到磁碟；事件入口不做檔案 I/O。底層統計最多等 100 毫秒，每個 Peer 至多一個取樣工作，避免診斷拖住測試結束。詳見 [封包分析的阻塞檢查與限制](NETWORK-DEBUG.md#診斷功能的阻塞檢查)。

重現前先完整結束兩端 YourDesk，再安裝診斷版並啟動，避免舊 Host 留在背景。停滯後保留兩端紀錄，記下大約時間；若通道完全失效，須重新連線後才能遠端讀取紀錄。此版本用於收集根因證據，並非宣稱停滯已修復。

## 控制通道壅塞時降低負載

控制 DataChannel 的 `BufferedAmount` 達 4 KiB 時暫停送入新影像分片，並捨棄此時的新滑鼠移動事件；降至 1 KiB 以下（含）才恢復，避免門檻附近反覆切換。按鍵按下／釋放、滑鼠按鈕、命令請求與回覆仍循可靠通道傳送，不任意清除。影像中途捨棄沿用既有 `ErrFrameDropped` 與影格恢復流程。這些門檻是初始實驗值，需要實際停滯測試驗證。

這不是清空 SCTP 內部佇列：Pion DataChannel 沒有提供維持可靠連線的 purge 介面。策略只減少繼續注入的流量，讓已排隊資料有機會送完；若底層路徑已失效，仍可能由既有存活檢查關閉。診斷版以 `control-backpressure` 事件記錄進入／退出及待送位元組數。不改變網路協定，舊端仍可互通；只在有此實作的一端生效。

## 大檔案傳輸的送出緩衝

檔案可由多個 pullWorker 同時讀取。現在剪貼簿通道依一般資料、讀取回覆／完成確認分別取得可取消的送出資格，再以共用鎖序列化「檢查 BufferedAmount → Send」，避免多個工作者同時通過同一個門檻。支援接收額度的兩端，會於應用層處理後歸還額度；慢速接收只讓傳送端等待，不丟棄檔案內容。等待可由工作階段或剪貼簿通道結束中止，詳見 [剪貼簿診斷](CLIPBOARD-DIAGNOSIS.md)。

檔案待送上限由 256 KiB 降為 64 KiB；畫面已有待送資料時，上限為一個最大剪貼簿訊息（20 KiB）。這只是上限，不是固定傳輸速率，可能降低高延遲連線的檔案吞吐量。修正應部署於檔案送出端；雙向傳檔需兩端更新。仍需以實際大檔案傳輸驗證是否解決原問題，不能由單元測試推定已修復。

## UDP socket 診斷

診斷版在原生 Pion 網路的 ListenUDP／DialUDP 所建立 socket 上觀測 ReadFrom／WriteTo，每五秒記錄 `udp-socket` 累計統計，關閉時再取樣一次。socket 為程序內序號，不是 IP 或 port。欄位包含讀寫回傳的正數位元組、資料報數、最大 UDP payload、超過 1200／1400／1472 bytes 的數量，以及 I/O 錯誤與短寫／讀取填滿 buffer 的次數。這些分桶只是觀測值，不是硬編碼 MTU 判定；讀取填滿 buffer 也不等於已證明截斷。

送出量採 WriteTo 的實際回傳，不再僅依 ICE 寫入前計數推定。觀測範圍是 Pion candidate 使用的 ReadFrom／WriteTo，不是整台電腦的封包擷取，亦不涵蓋其他程式、虛擬 Tailcat 傳輸或 socket 其他讀寫方法。未修改 MTU、封包內容及網路路由。配合兩端 UDP 與 ICE／SCTP 計數，縮小停滯發生的層級；仍不能單靠計數識別個別遺失封包。

## 被連線時間

macOS／Windows 的 Tray 選單在被連線期間，於「關閉程式」上方顯示「連線時間 HH:mm:ss」，每秒更新；展開選單時仍會更新。從本機偵測到被連線開始計時，斷線後隱藏，重新連線重新起算。時間使用系統單調計時，超過 24 小時不歸零；這是連線經過時間，不是閒置倒數。

## 斷線後自動重連（實驗功能，尚未發行）

設定新增「斷線後自動重連（實驗功能）」，預設關閉。與「斷線後自動關閉視窗」互斥：UI 開啟其中一項會關閉另一項；API 拒絕同時啟用兩項。此功能適用已開啟的遠端桌面視窗，不包含獨立命令列或未開視窗的 MCP 背景工作階段。

偵測到 Peer 結束後保留視窗與最後畫面，在背景依序嘗試三次，重試前分別等待 2、5、8 秒；各次協商與等待新畫面共用 30 秒期限。使用本次連線已驗證的密碼，不彈出密碼或重試錯誤視窗。只有收到且成功解碼新畫面並確認 Peer 已連線才算成功；成功後恢復同一視窗的操作與格式協商，之後再斷線會重新取得三次額度。三次失敗才結束視窗。

每次重試建立獨立 Peer、解碼器與剪貼簿工作階段，等待舊資源清理後才開始下一次，避免舊影格、參考幀與剪貼簿傳輸混入新連線。若舊原生工作者無法退出，重試會在等待清理時逾時，不會持續建立新的原生工作者。手動關閉視窗或 15 分鐘閒置自動關閉會直接結束，不觸發重連；重試中關閉視窗或停用自動重連會取消重試並關閉該視窗。

回歸測試包含第三次失敗終止、第一／二／三次成功後停止重試、等待與協商期間取消、每次逾時、舊工作者退出前不釋放資源、設定 API 拒絕衝突，以及前端兩個開關的雙向互斥。仍須實機驗證斷網、Host 重啟與長時間使用；此功能不能修復最初造成斷線的問題。
