# 更新三件套

「更新三件套」固定指：更新文件、上傳 GitHub、發布 Release。使用者要求執行時，依此順序完成，不只停在建置或打包。

1. 更新與本版有關的功能、錯誤修正及操作文件；Release 說明提供繁體中文、英文、日文、韓文，清楚標示實驗性功能與驗證限制。
   GitHub Release 標題使用 `YourDesk <版本>`；發行說明內文直接由 `## 繁體中文` 開始，不另放產品或版本的一級標題，避免頁面重複顯示。
   每次 Release 在本機準備根目錄 `release_zh-Hant.note`、`release_en.note`、`release_ja.note`、`release_ko.note`；這些檔案不提交到 GitHub 原始碼，每檔最多三行，僅寫使用者可理解的更新重點。`pack` 會將它們放入 GitHub Release 資產。新版本通知從 GitHub 讀取，更新完成後則從已安裝套件內的 note 檔顯示，使用者關閉更新重點後清除使用者更新狀態中的暫存內容，不刪除安裝目錄內的已簽章資源。
2. 檢查待提交範圍，保留不相關修改；確認編譯與語法後提交並推送 GitHub。除非另外要求，不增加功能測試。不得上傳私密設定、憑證或暫存備份。
3. 核對套件版本、目標架構、雜湊及 macOS 簽章／公證狀態，將 Release 標籤指向本次提交；先建立草稿並上傳完整套件與下載用 SHA-256 清單，核對後正式發布。

若已有涵蓋本次修改的完整套件，可使用該版本，不必重複建置。對外架構名稱使用 `x64`／`arm64`。發行說明應聚焦使用者可見的功能與修正，不把編譯成功描述成實機功能驗證成功。

Windows `pack` 同時產生同版同架構的 `-setup.exe` 與 `-service.zip`；每個 Windows 架構的兩個附件都必須上傳。後者供已授權服務自行更新，不列為一般 APP 安裝包。發布前從 GitHub API 核對服務 ZIP 的 `size` 與 `digest`（`sha256:`），並核對其 `manifest.json` 版本／架構；缺少服務附件或 GitHub 雜湊時，服務會拒絕更新，不會改以 UAC 安裝。測試版同樣需要完整附件。

## README 內容定位

四語 README 的「特色與功能」介紹整體專案的能力、用途與適用限制，不放版本號、build 編號、單次更新公告或開發分支進度，也不將功能寫成某一版的新增項目。各版更新與驗證紀錄放在 Release 說明或對應技術文件；發布新版時不要把該區塊改成更新日誌。平台限制、實驗性標示及必要的使用條件仍須保留。

## Release 標題與內文檢查（每次建立或修改都必做）

- 產品與版本標題只放在 GitHub Release 的標題欄：`YourDesk <版本>`。GitHub 已會顯示這個標題，內文不得再放 `# <版本>`、`# YourDesk <版本>`，也不得換成其他標題層級重複放置。
- 作為發布內文的 `docs/RELEASE-<tag>.md` 直接從 `## 繁體中文` 開始，接著依序為英文、日文、韓文段落；版本由檔名與 Release 標題識別。
- 使用舊文件時，先檢查並移除開頭的產品／版本標題；不可直接將含有重複標題的整份 Markdown 傳給 `--notes-file`。
- 發布前檢查草稿的標題欄與內文；發布後以 `gh release view <tag> --json name,body` 讀回核對，確認內文從語言段落開始，頁面沒有第二個版本標題。不能只檢查標題欄。
- 單純修正發行說明時，只更新內文，不改版本標籤、指向提交、發布狀態或下載附件。
